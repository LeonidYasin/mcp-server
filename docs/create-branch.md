# Создание и точное копирование веток

`create_branch(owner, repo, branch, from_branch="main")` создаёт только новый
`refs/heads/<branch>`. Существующие ветки не обновляются и не удаляются.

## Источники

- `from_branch`: имя ветки, tag/ref или SHA; разрешается через GitHub **Commits API**,
  а не через `git/ref/heads/<source>`. Если источник не указан — `main`.
- `from_sha`: полный 40-значный SHA коммита. Нельзя сочетать с `from_branch`.
  Возвращённый GitHub SHA обязан точно совпасть с запрошенным.
- SHA из форка работает, если GitHub позволяет целевому репозиторию разрешить этот
  коммит (обычно в общей fork network). Это не перенос объектов между несвязанными
  репозиториями и не обход прав доступа. Недоступный источник приводит к отказу до записи.

Для точной копии сначала прочитайте HEAD исходной ветки через `get_branch`, затем
передайте полный SHA:

```json
{
  "owner": "LeonidYasin",
  "repo": "glacier-mcp",
  "branch": "deploy/single-user-vps",
  "from_sha": "243e8583bcc373d51b62edb129f65c0f5a7bb173"
}
```

Один `POST /repos/{owner}/{repo}/git/refs` указывает на исходный коммит:
содержимое файлов, родители коммита и история сохраняются без merge, squash,
перезаписи файлов или новых коммитов. `main`, прочие ветки, теги и настройки
репозитория не меняются. Копирование одной ветки не означает зеркалирование
всего репозитория или удаление лишних веток.

## Защита и подтверждение

1. Проверить аргументы и разрешить источник один раз в полный SHA.
2. Проверить целевой ref. Только HTTP 404 означает отсутствие; ошибки доступа,
   лимита, сети и некорректный ответ блокируют запись.
3. Уже существующая ветка на том же SHA — успешный no-op; другой SHA — конфликт,
   без PATCH/force. Это намеренное ужесточение прежнего поведения «уже есть».
4. Отправить не более одного POST. При HTTP 422 перечитать ref для распознавания
   конкурентного создания, но не повторять запись.
5. После принятого POST независимо прочитать целевой ref и проверить тип commit,
   имя ref и точный SHA. Только подтверждённое совпадение сообщает об успехе.
   Неудачный read-back означает неопределённый результат, а не гарантированный
   откат: проверить `get_branch` перед повтором. Сетевой сбой POST также может
   скрывать успешно принятую запись.

Тесты в `tests/test_create_branch.py` используют настоящий `GitHubClient` с
`httpx.MockTransport`: внешние запросы, секреты и production не требуются.

После слияния изменения необходимо штатно обновить и перезапустить MCP-сервер,
а затем обновить обнаруженную клиентом схему инструментов. Сам PR не развёртывает
сервер и не выполняет копирование Glacier.
